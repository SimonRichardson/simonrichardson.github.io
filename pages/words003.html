Actors without the drama

On worker patterns in Juju, and how they accidentally became an actor system.

I've spent a good chunk of time working on Juju for my sins, which is a distributed system for deploying and managing workloads at scale. Hundreds of workers running concurrently, reacting to database changes, coordinating across machines. And somewhere in the middle of all that, there's a pattern that looks a lot like the actor model.

Workers as actors

A worker in Juju is dead simple on the surface. It's got Kill() and Wait() error. That's your contract. Start it, stop it, find out if it broke. Everything else is convention and composition.

But the interesting bit is how they wire together. Each worker is declared as a manifold - a description of what it needs (inputs) and what it provides (outputs). Inputs are named dependencies: "I need the database accessor, the agent config, the file notifier." Outputs are typed interfaces that other workers can consume. The dependency engine reads these declarations, works out the graph, and starts things in the right order.

Sound familiar? Each worker is an isolated unit of computation with a prescribed set of inputs and a typed output. They don't share memory. They communicate through the dependency graph and through event streams. The manifold is basically the actor's mailbox address and protocol definition rolled into one.

Events, not messages

Traditional actor models have mailboxes. Messages go in, the actor processes them one at a time. Juju does something different. The workload is heavily evented. Database changes flow through a change stream - transactions hit the database, a change stream picks them up, a stream worker serialises them into a sequence of terms, and an event multiplexer fans them out to subscribers.

Each worker subscribes to the events it cares about, filtered by namespace and type. When a change comes in, the worker reacts. It might update local state, trigger some API call, or start a child process. The key thing is it's pull-based with a push notification. You subscribe, you get told something changed, you decide what to do about it.

There's a twist though. If a subscriber doesn't act on an event in time - if it falls behind or stops consuming - the multiplexer boots it. No dead letter queue, no second chances. You're just out. It's then up to the worker to decide: do I resubscribe and catch up, or do I give up and die? Sounds harsh, but a stuck consumer can't block everyone else. That's the trade-off and it's a good one.

Behaviours live elsewhere

In a proper actor system you'd have behaviours - the ability for an actor to change how it handles messages based on state. Erlang's got gen_statem, Akka's got Receive swapping. Juju doesn't do that inside the worker. Instead, the concept gets pushed out into watcher implementations.

This wasn't some grand architectural decision. It just fell out of doing the work. Watchers are dead easy to test in isolation - you can throw a sequence of events at one without standing up the whole dependency engine. And you can reuse the same watcher logic across different workers. Separating "what do I watch" from "what do I do about it" turned out to be more useful than cramming both into the worker.

Supervision

Right, this is the good bit. Juju has three levels of supervision, each with different trade-offs.

The lightest is the catacomb. A worker owns a catacomb, and child workers get attached to it. If the parent dies, all the children die. If a child dies unexpectedly, the parent dies too. It's a shared fate model. Simple, brutal, effective. You use it when you've got a worker that spawns helpers and the helpers make no sense without the parent.

Next up is the worker.Runner. This gives you independent lifecycle management. Child workers can start and stop on their own terms, configured separately from the parent. The parent doesn't die just because a child restarts. You get something closer to Erlang's one_for_one supervision strategy, where each child is managed independently.

At the top sits the dependency engine itself. It manages the full graph of manifolds. It knows what depends on what. If a worker dies, it can restart it, which might cascade restarts through the dependency graph. Workers can restart themselves, pause, or remove themselves entirely - gracefully or not. The engine sorts it out.

Not quite actors, but near enough

I wouldn't put this in a textbook as an actor system. There's no location transparency. There's no formal message protocol. The "mailbox" is a subscription model that'll boot you if you're too slow. Behaviours live outside the actor boundary.

But the bones are there. You've got isolated units of work with typed inputs and outputs, event-driven reactions, hierarchical supervision. And it composes right well. You can wire manifolds together into proper complex distributed workflows, each one small and testable, each one reacting to changes without knowing owt about the bigger picture.

It's a reactive programming model for distributed systems. Not actors proper, but close enough to get the same benefits without dragging in a full framework. Nobody sat down and said "right, let's build an actor system." It just grew that way because the problems demanded it.
